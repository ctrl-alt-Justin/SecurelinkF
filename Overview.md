# SecureLink project overview

**Local development snapshot, November 26, 2026.** This is the starting point for the whole project, from the wearable and firmware through the Central System, companion app, research datasets, and thesis validation. It describes the files on disk. Verify implementation details against the current local source. Historical phase notes and packaged apps can represent older behavior.

**Thesis title:** SecureLink: Design and Development of a Compact NLP-Enabled Anti-Bullying Discreet Wearable Smart Badge Using Seeed Studio XIAO ESP32S3 Sense.

**Current stage:** USB-connected prototype with real recordings, paired audio diagnostics, and a temporary desktop transcript review tool. The next open milestone is USB reliability and emergency delivery. The V4 detection changes, persistent incident review, release packaging, and final thesis validation are still ahead. The [sprint plan](SPRINT_PLAN.md) targets December 30, 2026 for the implementation freeze.

## Purpose and scope

SecureLink is a thesis prototype for Philippine schools. A discreet wearable PIN captures nearby speech, and the Central System transcribes it and looks for possible verbal bullying, harassment, coercion, intimidation, or threats. The desktop dashboard helps an authorized adult review flagged incidents and their available evidence. The companion app provides paired mobile access to device status and incidents.

The PIN is a Seeed Studio XIAO ESP32-S3 Sense with an onboard microphone. The intended use is ordinary conversation at natural distances and speaking volumes. The system should handle Filipino, English, and Taglish, including code-switching within a sentence, and make uncertainty visible. A single microphone provides limited speaker and situational context. Treat every flag as a lead for human review. Speaker identity, intent, and disciplinary decisions require evidence beyond a transcript or severity score.

The current V4 scope is **USB-first verbal detection**. Wireless PIN transport, physical bullying detection, nonverbal behavior, and physiological monitoring are outside this phase. Existing Wi-Fi, BLE, camera, and tunnel code has its own history. Check source and deployed hardware before relying on those paths.

## How processing works today

1. **The PIN captures and segments speech.** The firmware uses I2S PDM microphone input, mono 16 kHz PCM16, Speex voice activity detection (VAD), and a ring buffer with about one second of pre-roll. The firmware has an approximately eight-second active stream cap. Natural speech can therefore appear across adjacent streams.
2. **USB delivers a completed utterance.** The Python USB manager discovers the COM port, identifies and authenticates the PIN, tracks heartbeat and VAD state, and assembles sequenced PCM frames. Keep USB presence, authenticated connection, microphone/VAD readiness, and inference state distinct. A plugged-in device can still have a failed handshake, stale heartbeat, or audio fault.
3. **The backend prepares the signal.** FastAPI receives the completed audio from the USB path. The processing function uses a high-pass filter, a denoising path that can use local NSNet2, conditional gain, and limiting. It produces processed PCM for playback when an incident is saved. PIN PCM and the exact float samples fed to Whisper are available through the opt-in diagnostic.
4. **Faster-Whisper transcribes and validates.** The server chooses `large-v3-turbo` on CUDA and `medium` on CPU. The shipped profile forces `tl`, uses an empty initial prompt, and enables internal VAD with threshold 0.40, minimum speech 250 ms, and padding 300 ms. Segment-confidence and lexical checks can reject speech or mark it uncertain. Only a nonempty `TRANSCRIBED` result proceeds to the live context engine. Preserve original recognized text separately from any analysis normalization.
5. **ContextEngine V3 estimates intent and severity.** Rules examine threat type, targeting, imminence, evidence reliability, and recent statements per device. The backend loads TagalogBERT weights, but the live scoring path does not invoke the classifier. An assessment includes richer context fields, while the main backend path currently uses score and category. `DANGER` starts at 8.0. The existing safety rules cap nonphysical or unreliable evidence below that threshold.
6. **The backend routes the result.** Conversational speech below 2.0 is eligible for the temporary local preview and bypasses incident creation. Other accepted results can create a recent incident, save processed WAV evidence, and broadcast an incident payload. The USB danger command currently hits a missing method before evidence is saved or broadcast. The firmware source recognizes the command and prints a serial alert. Physical alarm or camera behavior must be established separately on the deployed PIN.

Core paths are [firmware](esp32code.txt), [USB manager](securelinkdb/usb_manager.py), [backend and audio pipeline](securelinkdb/server.py), [denoising](securelinkdb/nsnet2.py), and [live context scoring](securelinkdb/context_engine.py).

### Local diagnostics and speech review

- **USB diagnostics** are off by default and explicitly enabled with `SECURELINK_USB_AUDIO_DIAGNOSTICS=1` before backend startup. They save up to five completed utterances per backend run in the private, Git-ignored `securelinkdb/.usb_audio_diagnostics/` directory. Each bundle can contain raw PIN PCM16, post-denoise/pre-gain float samples, and exact pre-VAD Whisper input with shared-window measurements. The worker writes metrics outside the transcription path. Missing stages and unreliable estimates are marked unavailable. Explicit diagnostics can capture ordinary speech. Follow the [diagnostic instructions](securelinkdb/README.md#local-usb-audio-diagnostics).
- **Show ordinary speech** is off by default. The opted-in desktop session receives up to 20 preview entries in memory with transcript, category, and severity. A person can type what was said and get a word-edit count, reference word count, and WER. The score uses the evaluator's normalization, is unavailable with an empty or unscoreable reference, can exceed 100%, and adds **Needs transcript review** only above 50%. Disabling clears the entries and references. This workflow has no effect on incident creation, severity, or alarm eligibility. Ordinary speech stays out of regular incident history, WAVs, transcript logs, and mobile broadcasts. [Desktop preview](securelinkdb/lib/ordinary_speech_preview.dart) · [Backend preview stream](securelinkdb/ordinary_speech_preview.py)

## What local evidence establishes

- The [application evaluation folder](securelinkdb/recordings/evaluation/) contains a main manifest with 22 entries, five of which have human references and are confirmed normal-distance conversations. A separate manifest has five more referenced recordings. Both manifests passed schema validation and all audio paths resolved. Keep the original five as development clips and the separate set as a baseline check. The five WAVs in `to annotate` contain distant background speech and belong in a separate cohort. Use only confirmed fan-, mouse-, or silence-only inputs to count false transcripts, outside speech WER.
- The five normal-distance clips measured **37 word edits across 101 reference words (36.6% WER)**. Peak normalization measured **38.6%**, and RMS gain measured **36.6%**. All three profiles preserved **4 of 9 expected negation tokens**. These results do not justify adopting either gain profile. Corpus analysis covered 239 recordings. The five reviewed clips' coverage of the lowest speech-active amplitude quartile remains unestablished.
- Four local diagnostic sessions contained 18 complete paired bundles at review time. In one reviewed short Filipino utterance, the speaker confirmed the complete phrase in both raw PIN audio and the saved Whisper input, yet the full-clip decode was unrelated. That case shows a recognition failure despite audible speech. One clip cannot establish the cause of every failure.
- The 300-scenario development set is synthetic and provisional. On it, V3 intent accuracy was **64.0%**, with **20/63 serious-threat misses** and **8/44 friendly-teasing false positives**. These are text development results. The local training CSV has 66 rows. Human-reviewed labels and an independent held-out set are still needed for model or release claims. [Development report](eval/reports/v3_dev300_baseline.md)
- The preview exists in local source. The normal Windows launcher pointed to a Release executable dated November 23, earlier than the November 25 preview source. Build from the current source before testing the feature in the installed-style workflow. The previous implementation pass recorded 19 targeted backend tests and five Flutter WER tests passing. The subsequent local review passed 11 evaluator tests. Physical preview, USB danger delivery, and the live tunnel remain unverified.

## Implementation priorities and requirements

1. **Make USB danger and evidence handling reliable.** `handle_completed_audio` calls `usb_mgr.send_line(...)`, which the USB manager lacks. Fix command delivery through the owning USB component, verify that a delivery failure cannot discard evidence, and test USB incident saving and broadcasting. Verify that inference state resets on completion, error, and reconnect. Isolate test stores before broader regressions because some provisioning/pairing tests can write application JSON. Confirm the actual PIN response during a controlled hardware test.
2. **Finish ASR evaluation and uncertainty routing.** Fix the evaluator's end-to-end reporting so a direct classifier fallback cannot stand in for a live incident. Compare one justified change at a time using identical inputs. Measure word edits, critical-word and negation errors, false transcripts on controls, rejection/uncertainty, and latency. Assess forced-language and fallback behavior, short Taglish phrases, VAD boundaries, and filters that can reject legitimate repetition or words associated with prompt echoes. Preserve accepted and rejected outcomes in evaluation. Design a human review path for uncertain transcripts carrying original text, optional normalized text, status, confidence, and authorized audio linkage. Uncertainty alone must never trigger emergency hardware; manual WER has no operational effect.
3. **Build and validate ContextEngine V4.** Establish a Filipino/Taglish rubric, human-review labels, and reserve independent held-out examples. Evaluate active TagalogBERT integration against V3 with a graceful rules fallback. Handle threats alongside negation, humor, quotations, and past or reported events. Account for friendly banter and ambiguous context without automatic escalation. Count repeated episodes separately from multiple chunks of one conversation. Report per-class results and serious-error slices.
4. **Persist incidents and secure access.** Implement the planned SQLite incident and reviewer store, retaining legacy response fields while adding assessment, confidence, and review metadata. Verify restart recovery and desktop/mobile behavior. Protect evidence, dashboard streams, and administrative endpoints and define who may see sensitive material, how long it is retained, and how it can be deleted. Keep temporary ordinary speech outside the persistent review store.
5. **Verify and package the release.** Build the current Windows app and exercise the real PIN for authentication, heartbeat, unplug/replug, reconnect during and after audio, natural Filipino/English/Taglish speech, incident evidence, and controlled alarm handling. Check the preview and public-tunnel isolation, then use independent human-reviewed fixtures for final evaluation. See the [acceptance criteria](SPRINT_PLAN.md#4-measurable-acceptance-criteria).

## Thesis validation and release evidence

- **Hardware and integration.** Record the tested firmware/build, physical PIN configuration, USB reconnect and heartbeat behavior, and the result of a controlled alarm and incident test. Record what was actually observed at the PIN, backend, and dashboard.
- **Speech recognition.** Report word errors, critical-word and meaning-changing negation errors, accepted/uncertain/rejected outcomes, false transcripts on confirmed non-speech controls, and latency. Include natural-distance speech and quieter captured signals. State the number and language mix of clips and distinguish development from held-out results.
- **Detection.** Compare the shipped V3 rules against the proposed V4 configuration on independent human-reviewed examples. Report per-class precision, recall, F1, and a confusion matrix, with errors for ambiguous teasing, missed serious threats, and incorrect emergency escalation. Track cases caused by ASR separately from those caused by scoring.
- **Product readiness and ethics.** Verify the packaged Windows workflow, incident recovery, review decisions, and evidence access. Document consent, retention and deletion, the limits of a single microphone, and the requirement for human review. Preserve the configurations, commands, and aggregate results needed to reproduce the evaluation while keeping private audio and references local.

## Running and changing the project

- Start the backend from `securelinkdb/` with `python server.py`, then check `http://127.0.0.1:8080/health`. Use `flutter run -d windows` from the same folder to test the current desktop source. Use `flutter build windows --release` to refresh the Release runner used by the root launcher. The mobile entry point is `lib/main_mobile.dart`.
- Use the existing test suites and evaluator. See [AGENTS.md](AGENTS.md) for dependency setup and commands. Run targeted tests after changes, broader regression suites at checkpoints, and Flutter analysis after Dart changes. Use mocked hardware and disposable stores before physical testing.
- Keep recordings, private references, and credentials local and out of Git and generated reports. Use consenting, authorized audio. Keep distinct boundaries between original evidence, normalized text, synthetic fixtures, and human-reviewed references. Preserve USB framing, API payload compatibility, and safety gates. Work only within the requested V4 scope and preserve `USBConnectionVersion`. Firmware changes, flashing, and public deployment require explicit authorization.
